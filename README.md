# 企业微信自动回复（Mac 桌面端方案）

基于 macOS 辅助功能 API，直接监听企业微信客户端未读消息并自动回复。

## 安装（新机器首次使用）

1. clone 本仓库
   ```bash
   git clone git@github.com:MarionLiew/wechat-autoreply.git
   cd wechat-autoreply
   ```
2. Finder 双击 `setup.command`，等脚本自动安装 Python/依赖
3. 系统设置 → 隐私与安全性 → **辅助功能** → 勾选 Terminal（或运行 Python 的终端）
4. 管理界面会自动弹出，按向导填 LLM API Key、规则等

## 日常启动

双击 `start.command`，浏览器自动打开管理界面（`http://localhost:8501`）。
在管理界面里启停守护进程、改规则、看消息日志、改高级设置。

## 调试日志

- `daemon.log` — 守护进程日志
- `debug-setup.log` / `debug-start.log` — 安装/启动脚本日志

## 核心文件

| 文件 | 作用 |
|---|---|
| `run.py` | 守护进程入口（轮询企微 Mac 客户端） |
| `admin/app.py` | Streamlit 管理界面 |
| `wecom/mac_watcher.py` | AX 读写企业微信 |
| `wecom/ai_panel.py` | 企微内置 AI 助手面板集成（实验性，见下方"企微内置 AI 回复"） |
| `reply/engine.py` | 规则 → RAG → 废话库 → LLM 多级回复（`WECOM_AI_ENABLED=false` 时的链路） |
| `reply/manual_alert.py` | 选座/改签等"需人工处理"关键词检测 + 邮件提醒 |
| `rules.json` / `fillers.json` | 规则库 / 废话库 |

## 后台控制模式

普通客户会话默认采用后台优先阶梯：`AXPress/AXSelected` → `CGEventPostToPid` →
读取当前聊天标题验证；只有确认后台操作无效后，才允许短暂激活企业微信前台兜底。
发送回复也会先用 PID 定向点击和回车，并以输入框清空作为发送成功依据。

```dotenv
BACKGROUND_MODE=true
ALLOW_FOREGROUND_FALLBACK=true
```

- `BACKGROUND_MODE=true`：启用后台优先模式。
- `ALLOW_FOREGROUND_FALLBACK=true`：后台验证失败时允许短暂抢前台，可靠性优先。
- 将 `ALLOW_FOREGROUND_FALLBACK=false` 可设为严格后台模式；后台操作失败时放弃本轮、
  记录日志并等待下轮，不会激活企业微信。
- 企微内置 AI 面板的唤出快捷键是系统级全局快捷键，无法承诺完全隐形；普通会话
  切换和发送不受此限制。

## 企微内置 AI 回复（实验性，2026-07-07 上线）

`WECOM_AI_ENABLED=true` 时，先用**企微自带 AI 助手面板**判断聊天消息方向，
再由面板生成回复。企微明确判断最近没有客户新消息时直接跳过；面板超时、
附加聊天失败或输出无法确认方向时也暂缓发送，**不把无方向的会话预览交给
RAG/LLM 猜测**。只有关闭此开关时，才使用本地规则/RAG/LLM 链路。
核心逻辑在 `wecom/ai_panel.py` 与 `wecom/mac_watcher.py`。

**关键实现细节**（踩过的坑）：
- 热键是**系统级全局快捷键**，必须用 `Quartz.CGEventPost(kCGHIDEventTap, ...)`
  发到全局事件流，`PostToPid` 发给 WeCom 进程无效。
- 每次生成前必须先点面板左上角"开启新对话"⊕按钮（`start_new_conversation`）：
  热键"关闭再打开"只是隐藏/显示，并不会真正清空会话历史，不点新对话会导致
  历史跨客户累积、且"和 XX 的聊天"这个 context chip 用过一次后就不再自动推荐。
- 附加聊天记录必须靠点击"和 XX 的聊天"这个 context chip，**不能靠手打客户
  原话进 prompt**——面板不点 chip 时有时读不到聊天记录会反问，点了 chip 才稳定。
  **`attach_contact_context` 找不到 chip 必须判定为失败（`return False`），
  不能放行**：早期版本认为"同一会话第二次不会再推荐 chip 所以找不到=已附加
  过"，但那是"面板沿用旧会话"时才成立的假设；后来改成每次都先点"开启新
  对话"重置，这个假设就不再成立了——2026-07-07 那次"AI 反问是哪位客户"的
  事故，根本原因就是 chip 真的没附加上（不是"已经附加过"），面板当时其实
  没有任何聊天记录可读，AI 只能瞎猜。现在改成找不到 chip 重试 5 次仍失败
  就返回 False，调用方据此回退原链路，不会在没有聊天记录上下文时硬生成。
- AI 回复必须用定界符（`===回复正文开始===`/`===回复正文结束===`）包住正文，
  程序按定界符提取——实测 AI 有时会把判断过程也混进回复正文（比如提到"这条
  需要转人工，我加个标记"），只靠"不要输出分析"这种口头约束防不住，必须靠
  定界符强制分离。**定界符缺失时必须判定为生成失败、返回 None 回退原链路，
  绝不能把未清洗的原始文本当兜底发出去**——2026-07-07 生产事故：客户马英枰
  只回了句"了解，谢谢啦"，AI 没走定界符格式，直接输出了一句语无伦次的追问
  （"您说的'这个客户'具体是指哪位客户？"），当时的兜底逻辑是退回整段原文，
  结果这句话被发给了真实客户（`_extract_final_reply` 现已改成定界符缺失时
  返回 `None`）。
- **纯致谢/确认类短消息不该走 AI 面板**：上面那次事故的根源之一是客户用繁体
  "謝謝"道谢，`rules.json` 里"谢谢"规则只匹配简体没接住，落到 AI 面板去对
  一句"谢谢"做"专业客服回复"生成，反而把 AI 绕懵了。已在 `rules.json` 里
  补了繁体致谢词规则和"了解/收到/好的"等纯确认短语规则，尽量在到达 AI 之前
  拦掉这类不需要真正生成的消息。
- prompt 里**必须**禁止"我是您的XX客户经理/客服[人名]"这类自我介绍开场白和
  "第一时间回复""有事请留言"等模板化措辞——南航对客户经理有"未回复率"考核，
  这类措辞会被公司审计系统识别成"自动回复"，即使真的回复了客户也按未回复
  扣分（详见内部审计表 `未回复明细` sheet，5.9% 的扣分案例是这个原因）。
- AI 判断"这条需要转人工处理"（选座/改签/退票/升舱等）时会在正文定界符
  之后附加内部标记 `[[NEEDHUMAN]]`，发给客户前代码强制剔除；`manual_alert.
  maybe_alert()` 拿这个当 `force_keyword`，跟客户原话的正则关键词匹配是
  两条独立信号，任一命中都发邮件提醒。
- **这是应答式客服，不是主动营销/引导式服务**：默认情况下 AI 倾向于在回复
  末尾主动加"要不我帮您查查里程""有什么想问的随时说"这类开放式反问或
  主动揽活的话术，看似热情，但客户一旦真的接话，后续都要客户经理去跟进
  处理，等于凭空增加工作量。已在 prompt 里明确要求只回应客户实际问到的
  内容，不主动引导、不主动推荐、不主动开放式反问。
- 2026-09-28：企微面板可以读到聊天双方的发言方向。若返回 `===无客户消息===`，或明确指出最近消息都是我方发出，属于**业务结论**而非生成失败，直接跳过，不调用二级 AI。
  群发后的会话预览没有方向信息；企微面板无法确认时宁可暂缓，也不交给二级 AI 猜。判断前不再发自动 `[玫瑰]`/`[握手]` 安抚，避免客户未发言时机器人先发消息。
- **语音/视频通话/语音消息**：AX 读到的语音消息/通话邀请显示为字面文本
  "[语音]"/"[语音通话]"/"[视频通话]"。客户经理没法处理，没有写死固定回复
  模板，而是在 prompt 里让 AI 自己组织语言告诉客户"这边设备听不了语音/
  接不了通话，麻烦打字说一下"——用词自然、每次可以不一样，比固定模板更
  像真人（这是特意的选择：先试过用 `rules.json` 写死一条正则规则，但会
  导致每次都是一模一样的机械措辞，改成交给 AI 生成，语气自然一些）。
  注意：`rules.json` 里"表情"规则(`\[.*\]`)原本是通用方括号匹配，会在
  wecom_ai 之前就抢先把"[语音通话]"当表情回一个"[握手]"，把这类消息拦在
  AI 前面。已把该规则改成 `\[(?!.*(语音|视频|通话)).*\]`(负向前瞻排除这几
  现在企微 AI 启用时先由面板判断方向，不再让该表情规则抢答；只有关闭面板模式后本地规则才生效。
  **历史教训**：旧版本在面板失败时回退到 `reply/engine.py`，旧链路有独立的
  `SYSTEM_PROMPT`，曾错误承诺回电话。保留两份行为约束，以供关闭面板模式时使用。

## 本地规则 / RAG / LLM 链路（关闭企微 AI 时使用）

2026-07-07：主 LLM 从 `LLM_PROVIDER=mimo` 切到了 `LLM_PROVIDER=custom`（配
`LLM_BASE_URL=https://openrouter.ai/api/v1` + `LLM_MODEL=deepseek/deepseek-
v4-flash`，key 复用原来 `OPENROUTER_API_KEY` 的值），因为 mimo 的 key 失效
了（daemon.log 里报了 177 次 `401 Invalid API Key`，每次都要空等 3 次重试
+ 切 moonshot 兜底，白白多耗几秒）。mimo 相关配置项还留在 `.env` 里没删，
以后 key 修好了可以直接把 `LLM_PROVIDER` 切回 `mimo`。
- 2026-09-28：AI 面板单次往返可能需要几十秒。为避免客户未发消息时机器人先发言，
  现在确认客户来信前不发送自动表情安抚。
- 2026-09-28：面板优先模式在消息方向存疑时（超时/附加失败/无法判定）按\"未确认\"处理，
  该轮宁可跳过也不调用二级 AI；只有 `WECOM_AI_ENABLED=false` 才走本地规则/RAG/LLM 链路。
- 经营线索处理前会强制关一次 AI 面板兜底——经营线索的 popup 查找用"最大
  非主窗口"策略，AI 面板如果没关成功会被误认成线索 popup。**反过来也一样**：
  `ai_panel._panel_window()` 是"找第一个非'企业微信'标题的窗口"，如果经营
  线索处理中途失败留下一个"线索详情"弹窗没关掉，AI 面板这边会把那个弹窗
  误认成自己的面板，导致找 chip/输入框全部找错窗口。2026-07-07 已加对称
  兜底：调用 `ai_panel.generate_reply` 前先 `self._close_xiansuo_popups()`
  清一次残留的线索弹窗（日志里确实抓到过一次：经营线索处理开始时关掉了
  一个 `CGSize(1000,720)` 的"弹窗"——那其实是没关成功的 AI 面板，尺寸完全
  对得上，说明这两边确实会互相干扰，加了对称兜底后双向都清）。

### chip 附加"失败"的真正原因：备注名 ≠ 微信号

之前怀疑过"语音通话消息导致 chip 不出现"，排查后证明是错的（用户指出后
重新排查确认）。**真正原因**：`attach_contact_context` 原来用
`"和" + 客户备注名 + "的聊天"` 精确匹配 chip 文字，但企微 AI 面板这个
chip 显示的是客户的**微信号/微信昵称**，不是我们 CRM 里给客户设的**备注名**
（比如某客户在我们这边备注是"刘明瑞(男)-3647"，但他真实微信号是别的
名字）——两者本来就是不同的字段，不是缓存或时序问题，多次"强制重启企微
仍复现"正好反证了这不是卡死/缓存，而是名字压根对不上。

**修复**：`_find_context_chip_button` 不再要求 chip 文字包含客户备注名，
只要求匹配"和...的聊天"这个固定格式（面板里同时只会有一个这种 chip，
不会跟"当前屏幕: ..."那个混淆），不管中间具体是什么名字都点。已用之前
"失败"过的联系人重新测试，确认修复生效。

排查过程中顺带发现并修了一个真 bug：`_send_hotkey()` 用 `CGEventSetFlags`
给空格键事件打 Control+Command+Option 标记，但从没发过这三个修饰键本身的
keyDown/keyUp，怀疑导致过残留修饰键状态，使后续点击会话行被系统误判成
Control+点击（=右键），弹出右键菜单而不是真正切换会话（跟用户反馈的
"用了右键，没切换"对应）。已加上：热键发完后显式发一遍这三个修饰键的
keyUp，防止残留。

## 已知限制

AX 层面**无法区分**聊天面板里某条消息是"我方"还是"对方"发的（都是 `AXStaticText`）。
本项目用多层防护缓解自回环：
1. 维护每个 sender 最近 `echo_protect_seconds`（默认 120s）内 bot 发出的回复，
   计数式地从 AX 读到的消息中扣除；
2. **不限时的 `_bot_sent_texts` 内容匹配兜底**（2026-07-07 加固）：AX 按气泡
   x 坐标判断左右方向，实测超长回复（AI 面板生成的回复偏长）偶尔会被误判成
   "客户"方向，导致 bot 自己发的历史回复被当成新客户消息又回复一次——仅
   靠 `echo_protect_seconds` 时间窗防不住"超过窗口"或"daemon 重启清空内存
   状态"这两种情况，现在额外用不限时的 `_bot_sent_texts`（按内容精确匹配，
   从 message_log 24h 历史加载）在 `all_msgs` 过滤时兜底，双重保险。
3. 若检测到 `tick` 的随机延迟期间客户又发了新消息，本轮放弃回复，下轮合并处理。

**仍然可能出错的场景**：
- **"经营大厅 / 快捷回复 / 人工客服"等功能面板作为浮层打开时**：会挡住聊天 AXWebArea，
  导致 bot 只能用会话行预览（最后一条消息）处理，无法读取完整多条上下文。
  日志会出现 `WARNING WebArea 黑名单` 提示。建议运行 bot 时保持聊天界面为活动视图，
  不打开功能浮层。
- **人工用同一企微账号手动回复**：不在 `_recent_replies_by_sender` 记录里，
  下轮 bot 会把人工消息当客户消息再次自动回复。建议人工介入时先在高级设置停掉 daemon。
- **消息发送半途失败**（写入成功但回车失败）：下轮可能重复。概率极低。
- **经营线索：聊天区是虚拟化列表**，只扫可视区渲染行会漏掉被滚出可视区的
  旧线索（2026-07-07 已加固：`_scan_leads_with_scroll` 反复滚动+扫描累积
  去重，直到连续两轮扫不到新内容才停；点击定位统一改成"用时按 hash 现找"）。

这两项可在未来通过 `AXPosition.x`（左右对齐）判断发送方来彻底解决，但需要更深的
AX 结构解析。
